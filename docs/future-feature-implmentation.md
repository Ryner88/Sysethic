# Future Feature Implmentation

This document captures practical next-step implementation work for SAAOE. Items are grouped by product area so future changes can be scoped into focused branches and commits.

## Security Hardening

### Authenticated Operator Sessions

Goal: require authenticated access before operators can view telemetry, trigger playbooks, download reports, or use the terminal.

Implementation outline:

- Add a user/session model backed by durable storage.
- Protect all HTML page routes and sensitive API routes with a shared authorization decorator.
- Add role checks for high-impact operations such as playbook triggering, automation rule creation, report download, and terminal use.
- Record login, logout, denied access, and privileged action events in audit logs.

Key routes affected:

- `/api/playbook_trigger`
- `/api/automation_rules`
- `/api/reports/download.<fmt>`
- `/api/terminal/status`
- `/terminal`

### Production Terminal Channel

Goal: replace the development diagnostic terminal with a production-safe terminal service.

Implementation outline:

- Terminate TLS before the WebSocket connection or run the terminal service behind a secure reverse proxy.
- Require a short-lived signed token when connecting to the terminal WebSocket.
- Keep the command allowlist and path restrictions.
- Add structured audit events for command attempts, blocked commands, command duration, timeout, and exit status.
- Add a server-side kill switch for the terminal service.

## Reliability and Persistence

### Durable Rule Storage

Goal: move in-memory anomaly rules, automation rules, playbooks, and run history into durable storage.

Implementation outline:

- Add tables or JSON-backed repositories for anomaly rules, automation rules, playbooks, and playbook runs.
- Replace module-level mutable globals with repository functions.
- Add created/updated timestamps and operator identity columns.
- Add duplicate suppression for automation and playbook actions across restarts.

### Telemetry Retention

Goal: formalize telemetry retention and prevent unbounded log growth.

Implementation outline:

- Add retention settings for `logs/system_log.csv`.
- Rotate or compact old telemetry into daily archives.
- Keep report generation compatible with archived data.
- Add index-like summaries for faster anomaly trend queries.

## Visualization Lab Enhancements

### Replay Controls

Goal: let operators scrub through historical telemetry rather than only viewing the latest ring buffer.

Implementation outline:

- Add API query parameters for time range and sample resolution.
- Add timeline controls for play, pause, step, and speed.
- Store current replay position client-side.
- Reuse the existing anomaly score and risk level model for historical windows.

### Correlated Event Overlay

Goal: overlay anomalies, playbook runs, terminal sessions, and audit events on Visualization Lab charts.

Implementation outline:

- Add an `/api/visualization_lab/events` endpoint.
- Return normalized events with `timestamp`, `type`, `severity`, `label`, and `target`.
- Render chart annotations and heatmap markers.
- Link annotations to anomaly detail, report, or audit log views.

## Reporting and Compliance

### Filtered Reports

Goal: allow reports to be generated by date range, severity, framework, and asset.

Implementation outline:

- Add query parameters to `/api/reports/summary` and `/api/reports/download.<fmt>`.
- Reuse `_load_anomalies(start, end, severity)`.
- Add framework and asset filters after anomaly decoration.
- Reflect active filters in CSV and PDF metadata.

### Evidence Bundles

Goal: export a response-ready bundle for a selected anomaly.

Implementation outline:

- Add `/api/anomalies/<id>/evidence`.
- Include anomaly detail, timeline events, top processes, network indicators, threat intel result, and related audit logs.
- Generate a zip bundle with JSON and CSV artifacts.
- Record the export in audit logs.

## Detection and Threat Intelligence

### Threat Intel Feed Management

Goal: make local threat intelligence easier to maintain and validate.

Implementation outline:

- Add a feed validation command.
- Add schema checks for IP, domain, and hash entries.
- Add an admin reload action that clears the in-process threat intel cache.
- Show feed status and last-modified time in the Security page.

### Detection Rule Testing

Goal: let operators test anomaly and automation rules before enabling them.

Implementation outline:

- Add a dry-run endpoint for proposed rules.
- Evaluate the rule against recent telemetry without persisting it.
- Return match count, latest matched sample, and predicted severity.
- Add rule validation errors for unknown metrics or unsupported operators.

## Frontend UX Improvements

### Loading and Error States

Goal: make data refresh failures visible without breaking the dashboard layout.

Implementation outline:

- Add reusable loading, empty, and error components in templates.
- Add client-side fetch wrappers with timeout handling.
- Surface stale data timestamps on cards and charts.
- Avoid repeated toast spam by suppressing duplicate notifications.

### Responsive Chart Layout

Goal: keep charts, tables, and alert panels legible on smaller screens.

Implementation outline:

- Audit each page at mobile, tablet, and desktop widths.
- Add table overflow containers where needed.
- Keep chart heights stable and avoid layout shift during refresh.
- Add visual regression screenshots for dashboard, anomalies, reports, and Visualization Lab.
